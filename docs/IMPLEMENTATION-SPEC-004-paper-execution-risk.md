# IMPLEMENTATION-SPEC-004 — Strategy-Neutral Paper Execution & Risk Engine

Status: **LOCK CANDIDATE AFTER GROK ADVERSARIAL REVIEW — NOT IMPLEMENTED**

Purpose: define the strategy-neutral paper execution, risk, reconciliation and audit infrastructure that can later support multiple strategies without altering their alpha logic.

This spec does not change TEST-SPEC-002, Strategy A, or closed TEST-SPEC-003.

## 0. Core invariants

1. Signals are immutable.
2. Infrastructure may approve/reject a locked strategy signal, but may not silently resize, delay, reverse, or rewrite it.
3. Last traded price is never treated as executable price.
4. Critical trading state must be durably persisted before downstream action.
5. No critical event may exist only in local process memory.
6. Retries/restarts must be idempotent.
7. Missing/stale/unverifiable execution data fail closed.
8. Position accounting is derived from fills.
9. Strategy-specific exits remain in strategy logic; infrastructure does not invent alpha exits.
10. Blind forward-test performance stays inaccessible before blind_until.
11. No live real-money routing is included in this implementation phase.

## 3. Durable queue / transactional outbox

Use Postgres/Supabase as the durable queue.

Table: `execution_outbox`

Fields:

- id
- event_type
- entity_type
- entity_id
- correlation_id
- payload
- available_at
- claimed_at nullable
- claim_expires_at nullable
- claimed_by nullable
- attempt_count
- processed_at nullable
- last_error nullable
- idempotency_key
- created_at

Unique:

`UNIQUE(idempotency_key)`

Workers claim rows atomically inside one database RPC using `FOR UPDATE SKIP LOCKED`.

A claim is a lease, not permanent ownership.

A row is claimable when:

- `processed_at IS NULL`, and
- `claimed_at IS NULL`, or
- `claim_expires_at < now()`

Reclaim must atomically replace `claimed_at`, `claim_expires_at`, `claimed_by` and increment `attempt_count`.

If a serverless worker dies after claim but before `processed_at`, another worker may reclaim only after lease expiry. State effects remain exactly-once through downstream canonical idempotency keys and atomic DB transactions.

No critical event is queued only in process memory.

If Supabase cannot persist the source event + outbox row atomically, processing fails closed.

Canonical outbox idempotency must include the logical event type:

`sha256("OUTBOX|" + event_type + "|" + entity_type + "|" + entity_id + "|" + logical_step)`

The key is generated by the server. Client-supplied arbitrary idempotency keys are not authoritative.

- REJECTED

`UNIQUE(signal_id, decision_stage)`

- entry time

### 4.1 Risk capacity reservation

Table: `risk_reservations`

Fields:

- id
- signal_id
- strategy_version_id
- pair
- side
- reserved_notional
- consumed_notional
- status: RESERVED | PARTIALLY_CONSUMED | CONSUMED | RELEASED
- policy_version_id
- created_at
- consumed_at nullable
- released_at nullable
- release_reason nullable
- state_version

Unique:

`UNIQUE(signal_id)`

Risk approval is one database transaction/RPC that:

1. locks the single `portfolio_risk_state` row for the paper account with `FOR UPDATE`,
2. reads current used exposure plus active reservations,
3. checks max-open and all configured capacity constraints,
4. inserts immutable `risk_decisions.APPROVED`,
5. inserts `risk_reservations` with `reserved_notional = intended_notional`,
6. updates reserved aggregates in `portfolio_risk_state`,
7. writes the required audit/outbox records,
8. commits atomically.

A rejected signal creates no reservation.

On a committed fill, reserved capacity is converted to used exposure in the same atomic fill-apply transaction. For a partial fill, only the filled notional is converted; the unfilled remainder stays reserved.

Unfilled reserved capacity is released atomically when the order reaches CANCELLED, EXPIRED or FAILED. A risk-approved order that is later rejected before fill also releases its reservation.

Two simultaneous signals cannot both consume the same capacity because all approvals serialize on the same `portfolio_risk_state` row. Do not use session advisory locks through a pooled Supabase connection.

## 5. Paper order state machine

Order states:

- CREATED
- ACCEPTED
- PENDING_FILL
- PARTIALLY_FILLED
- FILLED
- CANCEL_REQUESTED
- CANCELLED
- REJECTED
- EXPIRED
- FAILED

Risk approval exists before order creation; therefore `RISK_CHECKED` is not an order state.

Allowed transitions:

- CREATED -> ACCEPTED
- CREATED -> REJECTED
- ACCEPTED -> PENDING_FILL
- ACCEPTED -> CANCEL_REQUESTED
- PENDING_FILL -> PARTIALLY_FILLED
- PENDING_FILL -> FILLED
- PENDING_FILL -> CANCEL_REQUESTED
- PENDING_FILL -> EXPIRED
- PENDING_FILL -> FAILED
- PARTIALLY_FILLED -> FILLED
- PARTIALLY_FILLED -> CANCEL_REQUESTED
- PARTIALLY_FILLED -> FAILED
- CANCEL_REQUESTED -> CANCELLED

Terminal:

- FILLED
- CANCELLED
- REJECTED
- EXPIRED
- FAILED

Every transition creates an immutable `paper_order_events` row.

State meanings:

- ACCEPTED = the order is durably persisted, risk-approved and eligible for the simulator; it is not an exchange acknowledgement.
- EXPIRED = `max_order_age_ms` elapsed before the required fill completed.
- FAILED = execution could not be completed after ACCEPTED because of deterministic execution/internal failure such as insufficient book depth when partial fill is not allowed.
- REJECTED = the request failed ingest/risk validation before becoming executable.

### 5.1 Fill/cancel total ordering

Every fill-apply and cancellation transaction locks the same `paper_orders` row with `FOR UPDATE`.

Once `CANCEL_REQUESTED` or `CANCELLED` is committed, no new fill may be inserted.

A fill is valid only when its fill transaction acquires the order lock while the order is in an allowed fill state. Because fill insertion and order-state mutation are atomic, a fill committed before a later cancel request is already reflected in the order state before the cancel transaction acquires the lock.

Therefore SPEC-004 has no active `CANCEL_REQUESTED -> FILLED` transition.

A market snapshot whose `received_at` is after `cancel_requested_at` can never be used for that order.

Illegal transition => no mutation; emit critical audit/reconciliation issue.

## 6. Fill simulator v1

Paper market fills are deterministic.

Every candidate fill must reference an immutable persisted market snapshot.

Table: `execution_market_snapshots`

Fields:

- id
- pair
- provider
- provider_ts
- received_at
- bid_levels JSONB
- ask_levels JSONB
- best_bid
- best_ask
- snapshot_hash
- software_commit
- created_at

Unique snapshot identity is based on provider/pair/provider_ts/snapshot_hash.

Market order fill:

BUY:
- walk asks from best price outward
- consume actual base quantity until quote notional is filled

SELL:
- walk bids from best price outward

Compute:

- fill quantity
- VWAP
- spread
- depth consumed
- impact vs best price
- fee separately

No stochastic slippage.
No volatility penalty.
No last-price fill.

If depth cannot support required notional under the persisted snapshot:
- partial fill only if execution policy explicitly permits partial fill
- otherwise REJECT/FAILED with reason `INSUFFICIENT_BOOK_DEPTH`

No 5m candle-volume percentage rule.

Each fill references:

- order_id
- execution_attempt_id
- market_snapshot_id
- fill_seq
- fill quantity
- fill price
- fee
- spread_bps
- impact_bps
- filled_at
- idempotency_key

`fill_seq` is strictly increasing per order starting at 1 and is unique:

`UNIQUE(order_id, fill_seq)`

Position reconstruction always applies fills in `ORDER BY order_id, fill_seq`.

### 6.1 Deterministic execution attempt binding

Table: `paper_execution_attempts`

Fields:

- id
- order_id
- attempt_seq
- market_snapshot_id
- policy_version_id
- status: BOUND | APPLIED | REJECTED
- created_at
- applied_at nullable
- rejection_reason nullable
- idempotency_key

Unique:

- `UNIQUE(order_id, attempt_seq)`
- `UNIQUE(idempotency_key)`

The worker first durably binds one immutable market snapshot and policy version to an execution attempt. A retry reuses the same attempt/snapshot; it may not silently substitute a newer book for the same logical attempt.

Canonical attempt key:

`sha256("FILL_ATTEMPT|" + order_id + "|" + attempt_seq)`

Canonical fill key:

`sha256("FILL|" + order_id + "|" + fill_seq + "|" + execution_attempt_id)`

### 6.2 Partial-fill continuation

SPEC-004 chooses explicit continuation.

If `partial_fill_allowed = true` and the bound snapshot cannot fill the remaining quantity:

1. apply only the quantity deterministically available in that snapshot,
2. transition the order to `PARTIALLY_FILLED`,
3. convert only the filled share of the risk reservation from reserved to used,
4. keep the remaining notional reserved,
5. create a new outbox event for the remaining quantity with a new logical step / next attempt sequence,
6. the next attempt must bind a new market snapshot,
7. rerun execution-policy validity against that new snapshot before any additional fill.

No additional fill may reuse the previous snapshot.

If `partial_fill_allowed = false`, insufficient depth produces terminal `FAILED / INSUFFICIENT_BOOK_DEPTH` and the unfilled reservation is released.

## 8. Position accounting engine

Table: `paper_positions`

The position engine owns accounting state only.

It does NOT calculate strategy-specific entry/exit signals.

Required fields:

- id
- strategy_version_id
- pair
- side
- quantity
- average_entry_price
- gross_entry_notional
- cumulative_fees
- cumulative_execution_cost
- realized_pnl
- unrealized_pnl nullable/cache
- status
- opened_at
- updated_at
- closed_at nullable
- state_version

Allowed statuses:

- OPENING
- OPEN
- EXIT_PENDING
- CLOSING
- CLOSED
- RECONCILIATION_ERROR

Position state is reconstructed from immutable fills.

Accounting formulas for matched closed quantity `q`:

- long realized PnL = `(exit_vwap - entry_vwap) * q - allocated_entry_fees - exit_fees`
- short realized PnL = `(entry_vwap - exit_vwap) * q - allocated_entry_fees - exit_fees`

Execution impact/slippage is already embedded in fill VWAP and must not be deducted a second time. `cumulative_execution_cost` is diagnostic accounting only.

A fill that increases exposure is an entry fill. A fill that reduces/closes existing quantity is a closing fill. Only closing fills create realized PnL.

Use optimistic state_version plus DB locking/RPC for atomic updates.

Partial unique constraint:

only one active position per `strategy_version_id, pair` for strategies declared max_open=1.

Strategy-provided stop metadata may be stored, but stop generation remains outside this engine.

## 9.1 Risk clock and internal mark

`max_daily_realized_loss` uses the UTC calendar day:

`[00:00:00.000 UTC, 24:00:00.000 UTC)`

Daily realized PnL is produced only by closing fills according to the position-accounting formulas in section 8.

`max_intraday_drawdown` uses an internal paper-account equity mark built from persisted health-valid market snapshots. For an open long/short paper position, mark valuation uses the active internal mark policy; the policy version must be frozen before measurement.

The internal mark, marked equity, intraday drawdown and any derivative of them are sensitive performance data for a blinded strategy and must not be exposed before `blind_until`.

## 10. Kill switch

Global states:

- RUNNING
- HALT_NEW_ENTRIES
- HALTED
- RECOVERY_PENDING

Exact semantics:

### RUNNING
- new entry intents allowed subject to risk policy
- pending entry/exit orders may fill

### HALT_NEW_ENTRIES
- reject all new entry signals/orders
- no new entry risk reservation
- already-accepted/pending orders may complete deterministic fills
- risk-reducing strategy exit intents may still be accepted under their locked execution policy

### HALTED
- reject new entry intents
- do not create any new fill
- deterministically request cancellation of unfilled/partially-unfilled orders
- open positions remain recorded/frozen; do not fabricate a liquidation fill

### RECOVERY_PENDING
- same execution restrictions as HALTED
- health/reconciliation/recovery checks may run
- no new fill or new entry until explicit return to RUNNING

The fill-apply transaction must lock/read `kill_switch_state` in the same DB transaction. A fill may commit only when the current state permits fills.

Activation actions for HALTED:

1. reject all new signals/orders
2. cancel unfilled paper orders where cancellation is deterministic
3. prevent new fills from being created
4. mark open positions as risk-frozen for operational control

Do NOT automatically fabricate market liquidation during stale/missing-data conditions.

Emergency liquidation is a separate explicit policy:
- must be enabled/configured separately
- requires valid executable market data
- creates normal audited exit orders/fills

Automatic kill-switch trigger classes:

- persistence unavailable for critical write
- duplicate fill detected
- ghost fill
- impossible position quantity/side
- critical reconciliation failure
- audit integrity failure
- explicitly configured portfolio-risk breach
- explicitly configured market-data outage rule

Manual activation requires authenticated operator action and reason.

Reset:
- no automatic reset
- health checks pass
- reconciliation passes
- audit chain/checkpoint passes
- operator explicitly resets to RECOVERY_PENDING
- separate explicit enable returns to RUNNING

## 11. Reconciliation vs recovery

Reconciliation is read-only detection.

It may:
- emit issues
- escalate severity
- activate strategy/global halt

It may NOT directly repair orders/positions.

Recovery/Repair Worker performs an explicit, idempotent, audited action only after:
- issue identified
- repair rule exists
- repair action has unique idempotency key

Critical examples:

- fill without order -> HALTED
- position qty != fill-derived qty -> HALTED
- duplicate active position -> HALTED
- invalid audit hash/checkpoint -> HALTED

Warning examples:

- signal with no risk decision while still within processing SLA
- order awaiting worker claim but within age policy

## 12. Idempotency and concurrency

Required unique constraints:

- paper_signals(idempotency_key)
- risk_decisions(signal_id, decision_stage)
- paper_orders(idempotency_key)
- paper_fills(idempotency_key)
- execution_outbox(idempotency_key)
- recovery_actions(idempotency_key)

Order processing:
- atomic claim with `FOR UPDATE SKIP LOCKED`
- only claimed worker may transition order

Position update:
- DB transaction/RPC locks active position row
- insert fill + apply position update atomically where possible
- retry uses same fill idempotency key

Risk capacity:
- serialize capacity reservation using the paper-account `portfolio_risk_state` row lock inside one DB RPC
- do not use session advisory locks
- approved risk reservation is released/consumed deterministically by order/fill terminal effects

### 12.1 Canonical idempotency keys

All authoritative idempotency keys are generated server-side from canonical normalized fields.

Signal:

`sha256("SIGNAL|" + strategy_version_id + "|" + pair + "|" + side + "|" + signal_close_time_utc + "|" + rule_id)`

Risk:

`sha256("RISK|" + signal_id + "|PRETRADE")`

Order:

`sha256("ORDER|" + signal_id + "|" + intent_type + "|" + order_type)`

Outbox:

`sha256("OUTBOX|" + event_type + "|" + entity_type + "|" + entity_id + "|" + logical_step)`

Execution attempt:

`sha256("FILL_ATTEMPT|" + order_id + "|" + attempt_seq)`

Fill:

`sha256("FILL|" + order_id + "|" + fill_seq + "|" + execution_attempt_id)`

Recovery:

`sha256("RECOVERY|" + reconciliation_issue_id + "|" + repair_type)`

Client-provided random idempotency values may be logged as request metadata but never replace these canonical keys.

### 12.2 Atomic fill-apply transaction

A single DB RPC/transaction must perform all state effects of one fill.

It must:

1. lock `paper_orders`,
2. lock/read `kill_switch_state`,
3. lock the active `risk_reservations` and `portfolio_risk_state`,
4. load the bound `paper_execution_attempts` + immutable market snapshot,
5. re-check snapshot age/execution-policy validity,
6. verify order state permits fill and cancellation has not committed,
7. insert `paper_fills` with canonical idempotency and `fill_seq`,
8. update order status/filled quantity,
9. create or update `paper_positions`,
10. convert the appropriate reservation amount from reserved to used exposure,
11. update realized PnL if the fill closes quantity,
12. append order/position/audit events including the audit stream-head update,
13. mark the execution attempt APPLIED,
14. commit all changes atomically.

If any step fails, the transaction rolls back completely.

The outbox `processed_at` acknowledgement may be written only after the state-effect transaction is committed. Reprocessing the outbox event must observe the canonical idempotency rows and return the already-applied result rather than create a second fill.

## 13. Immutable audit model

Table: `execution_audit`

Append-only.

Fields:

- event_id
- event_type
- entity_type
- entity_id
- correlation_id
- strategy_version_id
- market_time nullable
- received_at
- decision_at nullable
- persisted_at
- state_before nullable
- state_after nullable
- input_snapshot_hash nullable
- reason_code
- worker_id
- software_commit
- stream_key
- stream_sequence
- prev_hash nullable
- event_hash

Use per-stream hash chaining, e.g.:

`stream_key = correlation_id` or stable aggregate id.

Unique:
- `UNIQUE(stream_key, stream_sequence)`
- `UNIQUE(event_hash)`

Table: `audit_stream_heads`

Fields:

- stream_key primary key
- last_sequence
- last_hash
- updated_at

Every audit append is performed inside a DB RPC/transaction that:

1. locks `audit_stream_heads(stream_key)` with `FOR UPDATE`,
2. reads the previous sequence/hash,
3. allocates `stream_sequence = last_sequence + 1`,
4. computes/inserts the next immutable audit row,
5. updates the stream head,
6. commits atomically.

This prevents two concurrent events on the same stream from allocating the same sequence or breaking the chain.

DB role/trigger must reject UPDATE/DELETE on audit rows.

A periodic checkpoint/root may later summarize stream heads.
